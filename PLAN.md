# PocketChat — Implementation Plan

A cross-platform (Android + iOS), terminal-styled chatbot app running a local LLM entirely on-device via llama.cpp, with lightweight persistent memory stored as plain `.txt` files. No servers, no cloud inference, no network calls except deliberate model downloads.

## Decisions locked in so far

| Area | Decision | Why |
|---|---|---|
| Inference engine | **llama.cpp** (not bitnet.cpp) | Full GGUF model ecosystem, actively maintained, supports downloading/switching models |
| Platforms | Android + iOS, **shared C++ core + thin native UIs** | Zero framework overhead beyond the model itself; Kotlin/Jetpack Compose (Android), Swift/SwiftUI (iOS), both styled as a terminal |
| Minimum spec floor | **~3GB usable RAM**, roughly devices from the last 6-7 years | User's floor; covers old-but-not-ancient hardware without crippling the default experience |
| Default model | Small model in the ~1-1.5B param range, Q4_K_M quant (few hundred MB) | Fits comfortably on the floor-spec device |
| Model switching | In-app model manager: download/delete/switch between GGUF models | User has a 12GB S25 Ultra and wants to opt into bigger models (3B/7B/8B) when hardware allows |
| Memory | Not raw chat transcripts. **User-fact memory + rolling session summaries**, plain `.txt`, generated by the model itself | Keeps context small and relevant instead of unbounded history |
| Storage | 100% local — models + memory files in app-private storage | No reliance on external hardware/services |
| Builds | **GitHub Actions**, not local — Android via NDK on a Linux runner, iOS via a macOS runner + Xcode. Artifacts downloaded from the workflow run. | User's phone builds locally were a non-goal from the start; also removes the "need a Mac" blocker for iOS |
| Repo/tools | `pocketchat/` created at `/root/termux_home/projects/pocketchat`, git identity set (`O-xix` / `ichorlifephoenix@gmail.com`), `gh` installed but **not authenticated** (device-code login kept timing out — revisit later with SSH key or PAT when we're ready to push) | |

## UI / Visual design

Inspired by Android recovery/download-mode screens (power+volume-down menu) — **visual only**, not a system dependency (that environment is bootloader-level and inaccessible to apps; there's nothing to literally hook into). Hardware volume-button navigation was considered and explicitly declined — normal touch/keyboard input only, since iOS restricts hardware-key interception much more than Android and it'd be inconsistent across platforms anyway.

- **Font**: bundle a single open-license monospace font (e.g. JetBrains Mono, SIL OFL) identically on both platforms, rather than relying on each OS's default monospace — keeps the look consistent instead of drifting per-device
- **Palette**: black background, high-contrast foreground (white/green), sparing use of an accent color for warnings/status — no gradients, no rounded chrome
- **Layout**: chat screen is a scrolling text buffer with streaming token output, like a terminal; the model manager and settings screens use a flat text-menu list style rather than typical mobile cards/tabs

## Architecture

```
pocketchat/
├── core/                    # Shared C++ layer — the only place model logic lives
│   ├── llama.cpp/           # vendored dependency (git submodule)
│   ├── inference/           # thin wrapper: load/unload model, generate, tokenize
│   ├── memory/              # fact-extraction + summarization prompts & .txt read/write
│   └── CMakeLists.txt
├── android/                 # Kotlin + Jetpack Compose app
│   ├── app/
│   │   ├── jni/             # JNI bridge into core/
│   │   └── src/             # terminal UI, model manager screen, chat screen
│   └── build.gradle.kts
├── ios/                     # Swift + SwiftUI app
│   ├── PocketChat.xcodeproj
│   ├── PocketChat/          # terminal UI, model manager screen, chat screen
│   └── PocketChatCore.xcframework build script (wraps core/ for Swift interop)
├── .github/workflows/
│   ├── android-build.yml    # assembles + uploads debug/release APK as artifact
│   └── ios-build.yml        # builds .ipa (or sim build) on macos-latest, uploads artifact
└── docs/
    └── models.md            # curated list of tested GGUF models per hardware tier
```

**Why a shared C++ core instead of Flutter/React Native:** the model dominates RAM/CPU cost either way, so a cross-platform UI framework wouldn't meaningfully increase overhead — but native UI keeps every layer under our control on hardware that's already tight on resources, and avoids a second runtime (Dart/JS VM) competing for memory with the model.

## Phases

### Phase 0 — Repo scaffolding
- Initialize git repo, `.gitignore` (build artifacts, downloaded models, NDK/Xcode caches)
- Add `llama.cpp` as a git submodule in `core/llama.cpp`
- Empty Android (Gradle) and iOS (Xcode) project skeletons
- CI workflow stubs that just build "hello world" on both platforms, to validate the pipeline before any real code lands

### Phase 1 — Core inference wrapper (`core/inference/`)
- Thin C API over llama.cpp: `load_model(path, n_ctx, n_threads)`, `generate(prompt, callback)`, `unload_model()`
- Memory-conscious defaults: mmap model loading, conservative context window (e.g. 2048) on the low tier, larger on high tier
- Runs and is testable standalone on this Linux/Termux environment before touching mobile UI at all

### Phase 2 — Android app
- JNI bridge to `core/`
- Terminal-styled chat UI (Compose): monospace, scrollback, streaming token output
- Model manager screen: list bundled/downloadable models with size + RAM requirement, download with progress, delete, switch active model
- Basic on-device RAM detection to recommend a tier (not enforce — user can still pick a heavier model)

### Phase 3 — Memory system (shared, used by both platforms)
- After each session (or every N turns), prompt the *loaded model itself* to:
  1. extract/update durable facts about the user → `memory/profile.txt`
  2. append a short summary of the session → `memory/summaries/<timestamp>.txt`
- On session start, inject `profile.txt` + the last few summaries into the system prompt (bounded size, oldest summaries pruned/compacted over time)
- All memory is plain text, human-readable, user-editable/deletable from the filesystem

### Phase 4 — iOS app
- Swift/SwiftUI port of the same UI concepts, calling `core/` via an XCFramework
- Written and buildable-by-CI from this session; actual on-device install/testing is on you (needs Xcode + eventually an Apple Developer account for real-device signing — simulator builds don't need one)

### Phase 5 — GitHub Actions CI
- `android-build.yml`: Gradle assemble, upload `app-release-unsigned.apk` (or debug APK) as a workflow artifact
- `ios-build.yml`: `xcodebuild` on `macos-latest`, upload `.xcarchive`/simulator build as artifact; document the extra steps needed later for a signed, sideloadable `.ipa`
- Both triggered on push/PR, plus manual `workflow_dispatch`

### Phase 6 — Model tiering & docs
- `docs/models.md`: curated, tested GGUF models per RAM tier (e.g. ~3GB floor / ~6GB / ~12GB+), with download links and expected tokens/sec ballpark
- In-app tier presets map to this list

### Phase 7 — Polish & test matrix
- Test on the S25 Ultra (high tier) directly
- Test low-tier behavior via constrained emulator profiles (throttled RAM/CPU) since we don't have a physical old device
- iOS testing matrix depends on what devices/simulators you have access to

## Open items to decide later (not blocking start)

- **iOS signing**: real-device installs need an Apple Developer account ($99/yr) and provisioning profile; CI can produce simulator/unsigned builds without one. Revisit when ready to actually install on an iPhone.
- **git push auth**: `gh auth login` device flow failed twice (expired before completing). Will set up an SSH key or PAT when we're ready to push to GitHub.
- **Default model pick**: needs a concrete choice (candidates: Qwen2.5-1.5B-Instruct-GGUF, Llama-3.2-1B-Instruct-GGUF) — finalize in Phase 6 once we can benchmark actual tokens/sec on both the floor-spec target and the S25 Ultra.

## Non-goals

- No cloud fallback / hosted inference
- No local on-device APK/IPA compilation as the primary build path (CI-only, per your instruction)
- No comprehensive raw chat-log storage
